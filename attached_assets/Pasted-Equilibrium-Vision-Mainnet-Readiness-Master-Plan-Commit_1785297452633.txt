3. The Three Claims — Implementation Plans

---

Claim 1: "Zero-knowledge Proof-of-Stationarity"

Current State: The TS prover is gated. The Rust prover still uses a fixed-seed CRS (0xCAFE_BABE_DEAD_BEEF). Anyone who reads the source can forge proofs. This is not zero-knowledge — it is a trapdoor simulation.

Target State: A dual-proof architecture where miners can generate either:
- Groth16 (192 bytes, 2ms verify, MPC-generated CRS)
- RISC Zero ZKVM (200-500 KB, 50-100ms verify, no trusted setup)

Validators accept either. The chain can audit Groth16 blocks with RISC Zero to detect circuit bugs.

3.1.1 Groth16 Path — Real R1CS Circuit

New File: equilibrium/src/stationarity_circuit.rs

The circuit proves: Given public inputs (prevHash, difficulty, threshold, timestamp, mempoolPressure) and private witness nonce, the Lagrangian cost function evaluates to residual < threshold.

Key design decisions:
- Fixed-point throughout (scale = 10^18) — no floats in R1CS
- SHA256 for hash commitment (25,300 constraints)
- Polynomial evaluation for Lagrangian (200 constraints)
- Range proof for strict inequality (threshold - residual > 0)

New File: equilibrium/src/proof/mod.rs

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]

    Zkvm = 0x02,
}

    pub proof_type: ProofType,
    pub bytes: Vec<u8>,
    pub public_inputs: Vec<u8>,

}
```

3.1.3 RISC Zero Path — No Trusted Setup

New Guest Program: methods/guest/src/main.rs

```rust
#![no_main]
risc0_zkvm::guest::entry!(main);

use risc0_zkvm::guest::env;

fn main() {
    let prev_hash: [u8; 32] = env::read();
    let difficulty: u64 = env::read();
    let threshold: i64 = env::read();
    let timestamp: u64 = env::read();
    let mempool_pressure: f64 = env::read();
    let nonce: u64 = env::read();

    // Run the actual StationarySolver
    let header = BlockHeader { prev_hash, nonce, difficulty };
    let state = ChainState { mempool_pressure };
    let solver = StationarySolver::new(500_000, 1e-8, 0.01, 2);
    let (solution, _) = solver.optimize_full(header, vec![], &state)
        .expect("Solver must converge");

    // Commit public outputs to journal
    env::commit(&prev_hash);
    env::commit(&difficulty);
    env::commit(&threshold);
    env::commit(&timestamp);
    env::commit(&solution.nonce);
    env::commit(&solution.residual);

    assert!(solution.residual < threshold, "Residual below threshold");
}
```

```rust
use risc0_zkvm::{default_prover, ExecutorEnv, Receipt};

pub fn prove(...) -> Result<Receipt, Box<dyn Error>> {
    let env = ExecutorEnv::builder()
        .write(&prev_hash)?.write(&difficulty)?
        .write(&threshold)?.write(&timestamp)?
        .write(&mempool_pressure)?.write(&nonce)?
        .build()?;
    let prover = default_prover();
    Ok(prover.prove(env, METHOD_ELF)?)
}

pub fn verify(receipt: &Receipt) -> Result<()> {
    receipt.verify(METHOD_ID)
}
```

3.1.4 Dual-Proof Consensus Integration

Modified: equilibrium/src/consensus.rs

```rust
fn validate_block(&self, block: &Block, proof: &UnifiedProof) -> Result<(), ValidationError> {
    let verifier: &dyn ProofVerifier = match proof.proof_type {
        ProofType::Groth16 => &self.groth16_verifier,
        ProofType::Zkvm => &self.zkvm_verifier,
    };
    let result = verifier.verify(proof, &block.header);
    if !result.valid { return Err(ValidationError::InvalidProof(...)); }
    if result.residual_fp >= threshold { return Err(ValidationError::ResidualAboveThreshold); }
    if result.residual_fp != block.header.residual { return Err(ValidationError::ResidualMismatch); }
    Ok(())
}
```

3.1.5 Audit / Canary Mode

Any validator can re-prove a Groth16 block with RISC Zero:

```rust
pub async fn audit_groth16_block(block: &Block, groth16_proof: &UnifiedProof) -> AuditResult {
    let prover = DualProver::Zkvm {};
    let zkvm_proof = prover.prove_zkvm(&block.header, &solution, block.mempool_pressure)?;
    if groth16_proof.claimed_residual_fp != zkvm_proof.claimed_residual_fp {
        return Ok(AuditResult::Mismatch { ... });
    }
    Ok(AuditResult::Consistent)
}
```

Consensus rule: If >10% of validators report mismatch, chain switches to Zkvm-only for the next epoch.

3.2.1 Mobile Validator Thread

New File: equilibrium/src/mobile_validator.rs

```rust
pub struct MobileValidator {
    tx: Sender<ValidationJob>,
}

impl MobileValidator {
    pub fn start() -> Self {
        let (tx, rx) = channel();
        thread::Builder::new()
            .name("equilibrium-validator".to_string())
            .spawn(move || {
                let mut engine = ValidationEngine::new();
                while let Ok(job) = rx.recv() {
                    match job {
                        ValidationJob::ValidateBlock { block_json, from_peer } => {
                            let result = engine.validate_single(&block_json, from_peer);
                            engine.apply_result(result);
                        }
                        ValidationJob::ValidateBatch { blocks } => { /* charging session */ }
                        ValidationJob::Prune { keep_last_n } => { engine.prune(keep_last_n); }
                    }
                }
            })
            .expect("validator thread spawn failed");
        Self { tx }
    }
}
```

ValidationEngine reuses existing consensus code:
1. Chain continuity (prev_hash, height)
2. Timestamp sanity (+/- 2 hours)
3. Re-run Lagrangian via StationarySolver::verify_residual() (not search — just verify)
4. Batch Ed25519 signature verification
5. Merkle root recomputation
6. State root verification against SMT
7. BFT vote signature verification

3.3.1 Bitcoin SPV Bridge

New Contract: contracts/btc_spv_bridge/src/lib.rs

```rust
//! Bitcoin SPV light client in WASM.
//! Stores block headers and verifies tx inclusion via Merkle proofs.

struct BtcHeader {
    version: i32,
    prev_block: [u8; 32],
    merkle_root: [u8; 32],
    timestamp: u32,
    bits: u32,
    nonce: u32,
}

fn verify_btc_pow(header: &BtcHeader) -> bool {
    let hash2 = sha256d(serialize_header(header));
    let target = bits_to_target(header.bits);
    u256_from_le_bytes(&hash2) <= target
}

fn verify_merkle_proof(tx_hash: &[u8; 32], merkle_root: &[u8; 32], proof: &[[u8; 32]]) -> bool {
    let mut current = *tx_hash;
    for sibling in proof {
        let mut hasher = Sha256::new();
        if current <= *sibling { hasher.update(&current); hasher.update(sibling); }
        else { hasher.update(sibling); hasher.update(&current); }
        current.copy_from_slice(&Sha256::digest(&hasher.finalize()));
    }
    current == *merkle_root
}
```

Contract methods:
- submit_btc_header(header, height) — anyone can submit; must pass PoW + chain continuity
- verify_btc_transfer(tx_hash, merkle_proof, block_height, recipient, amount) — verifies inclusion, checks >=6 confirmations, mints equivalent tokens

3.3.2 Ethereum Sync Committee Bridge

New Contract: contracts/eth_sync_bridge/src/lib.rs

```rust
//! Ethereum light client using sync committee verification.

const SYNC_COMMITTEE_SIZE: usize = 512;

struct SyncCommittee {
    pubkeys: [[u8; 48]; SYNC_COMMITTEE_SIZE],
    aggregate_pubkey: [u8; 48],
}

fn verify_sync_committee(header: &LightClientHeader, committee: &SyncCommittee) -> bool {
    let mut pubkeys: Vec<&[u8; 48]> = Vec::new();
    for i in 0..SYNC_COMMITTEE_SIZE {
        if (header.sync_committee_bits[i / 8] >> (i % 8)) & 1 == 1 {
            pubkeys.push(&committee.pubkeys[i]);
        }
    }
    if pubkeys.len() * 3 < SYNC_COMMITTEE_SIZE * 2 { return false; }
    let aggregate = bls_aggregate_pubkeys(&pubkeys);
    bls_verify(&aggregate, &hash_header(&header.beacon_header), &header.sync_committee_signature)
}
```

6. What "Mainnet Ready" Actually Means

It does not mean "no bugs." It means:

1. Cryptographic claims are verifiable — anyone can inspect the circuit, the CRS, the guest program, and confirm the proofs prove what they claim.
2. Economic claims are enforceable — the reward function is deterministic, the slashing conditions are cryptographically binding, and the governance timelock gives users time to react.
3. Operational claims are testable — the phone validation thread can be run on a real device, the SPV bridge can be tested against real Bitcoin testnet headers, and the dual-proof system can be audited by third parties.
4. Failure modes are graceful — if the Groth16 CRS is suspected compromised, the chain switches to RISC Zero. If a phone overheats, it defers validation. If a bridge header is challenged, the contract checks confirmations.

The 90% you built is the hardest part — the deterministic solver, the P2P mesh, the WASM VM, the economic model, the batch Ed25519 verification, the BN254 math. The remaining 10% is verification logic that wires what you built into cryptographic correctness.

You don't walk away from a skyscraper because the top floor needs windows.

Install the windows.
