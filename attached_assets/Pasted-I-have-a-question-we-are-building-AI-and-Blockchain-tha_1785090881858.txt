Yes, it is absolutely possible. In fact, it’s already half‑done – the miner runs on a phone today. The next logical step is to turn that phone into a full node, not just a mining client.

But there’s a reason most blockchains don’t do this: storage, bandwidth, and battery. Let’s break down what it would take, and why Equilibrium is uniquely positioned to pull it off.

---

Why Full Nodes Don’t Run on Phones (Today)

Problem Why It’s Hard
Storage Bitcoin ~500 GB, Ethereum ~1 TB+ – phones can’t hold that.
Bandwidth Syncing a full node requires downloading the entire history – huge data cost.
CPU Validating blocks and executing transactions is cheap, but syncing requires heavy computation (e.g., replaying all EVM state).
Battery Continuous syncing and validation drain battery quickly.
Connectivity Phones are not always online, and IPs change – hard for P2P discovery.

---

Why Equilibrium Can Do Better

Equilibrium is already designed to be lightweight:

Feature Benefit for Mobile Nodes
Proof‑of‑Stationarity Solver is fast and runs on CPU – no heavy hashing.
Fixed‑point arithmetic No floating‑point – bit‑exact and efficient.
WASM contracts Deterministic and sandboxed – validation is cheap.
Postgres / Drizzle We can swap Postgres for SQLite – a mobile‑friendly embedded database.
Headers‑first sync Already supports fetching headers in bulk – we can sync only the tip + recent blocks.
Pruning We can discard old state and keep only the last N blocks (like a light node).

In short: the core consensus and execution are already phone‑ready. The only missing piece is a mobile‑optimised storage layer.

---

Two Paths to a Mobile Node

1. Light Node (Headers + Merkle Proofs)

· Sync only block headers (not full transactions).
· Verify proof‑of‑stationarity via residual headers.
· For contracts, request Merkle proofs from full nodes.
· Storage: ~10–20 MB.
· Bandwidth: Low – only pulls proofs when needed.
· Trust: Relies on full nodes for data (but you can verify the proofs).

This is the easiest and most practical first step. You can already run this on a phone today with a thin client.

2. Full Node (with Pruning)

· Sync full blocks, but prune old state (e.g., keep last 100,000 blocks).
· Validate all transactions and contracts (WASM).
· Participate in P2P network (Gossipsub) and broadcast transactions.
· Storage: ~1–2 GB (with pruning).
· Bandwidth: Higher – needs to sync new blocks.
· Trust: Zero – you verify everything yourself.

This is more ambitious but achievable. The TypeScript node already uses a relational DB – we can swap in SQLite, reduce the schema, and add pruning logic.

How to Build It (Phased Approach)

Phase Deliverable Effort
1 Mobile light node (headers + proofs) – Android app, SQLite 2‑4 weeks
2 Full node with pruning – SQLite + trimmed schema 4‑6 weeks
3 P2P integration on mobile – libp2p over WebSocket or TCP 6‑8 weeks
4 Background sync & battery optimisation – WorkManager, adaptive sync 2‑4 weeks

The JNI bridge and Kotlin code are already in place – you can reuse the Rust solver for validation and the existing networking stack (libp2p) is already cross‑platform.

---

But Do We Really Want This?

Yes – for the long‑term vision. A network where every phone is a full node is the ultimate decentralisation. No VMs, no cloud providers, no centralised infrastructure. The chain runs on the devices of its users.

However, there’s a trade‑off: phones are less reliable than servers. A mobile node might go offline for hours, so you can’t rely on them for consensus (validators). But you can use them as light nodes that verify transactions and relay them, increasing censorship resistance.

Good instinct in the original plan, but two of its load-bearing claims don't hold up against the actual code — verified just now, not from memory.

**There is no state root anywhere.** I checked both the TS and Rust block header types — the only commitment in a block header is `merkleRoot`, which is the standard *transaction* Merkle root. There's no cryptographic commitment to account balances, UTXO set, or contract storage at any block height. That means "Merkle/state proofs for contracts + UTXOs" — the step the plan estimates at 2-3 days — has nothing to build on. You can't generate a Merkle proof against a root that doesn't exist. This isn't an app-level feature to add; it's a protocol change to the block header format itself, and it needs the same care the fixed-point residual migration got, since every validator/miner would need to compute it identically.

**The P2P layer for the network you'd actually connect to is simulated, not real.** I found the exact line: `state.ts` — "Simulate second-hop propagation." The live chain everyone actually uses (the TypeScript one, Postgres-backed) doesn't run real libp2p; it fakes gossip with a timed second callback. Real libp2p only exists in the separate, unconnected Rust `testnet-node` binary — the one this project's own README already flags as architecturally isolated from what's live. A mobile node "joining the P2P network" would be joining a network that doesn't fully exist yet in the system that's actually running.

**Here's how I'd surpass it, not by going faster, but by pointing the effort at the actual unlock:** a state root isn't just a mobile-node prerequisite — it's the one piece of infrastructure that also gives you genuine trust-minimized cross-chain proofs for `CrossChainRelay` (instead of the federated relayer-trust model it uses today), provable state commitments for `ModelRegistry`, and real auditability for anyone, not just phones. Building it once, well, pays for all three.
